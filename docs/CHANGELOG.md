## 오답노트 49개가 1/20으로 보이던 것

- 오답노트는 한 번에 20개만 꺼내면서 그 묶음의 길이를 진도 분모로 썼다. 오늘 복습 대상이 49개여도 첫 카드가 `1/20`으로 보여 전체 진도처럼 읽혔다.
- 20개씩 푸는 흐름은 유지하고, 분모와 진행 막대는 오늘 대상 전체를 기준으로 계산한다. 첫 묶음을 마치면 `20/49`와 남은 29개를 보여 주고, 다음 묶음으로 이어갈 수 있다. 마지막 9개까지 마쳐야 완료 화면이 나온다.
- 묶음 사이에 오답노트를 나갔다 돌아와도 진행 수가 초기화되지 않게 했다. `node tools/review-test.js`로 49개와 8개인 경우를 확인했다.

## 다른 기기 진도가 사라지거나 화면에 늦게 보이던 것

- 학습 뒤 15초가 지나거나 앱을 덮을 때, 서버 사본을 읽지 않고 이 기기 자료를 통째로 올렸다. 그 사이 다른 기기가 쌓은 진도가 서버에서 사라졌다. 모든 업로드가 먼저 서버를 읽고 합치도록 바꿨다.
- 두 기기가 같은 서버 판을 읽고 함께 쓰면 늦게 쓴 쪽이 앞의 기록을 덮을 수 있었다. Firestore 문서의 갱신 시각을 조건으로 쓰고, 조건이 어긋나면 최신 판을 다시 받아 합친다.
- 받은 자료는 저장소에만 쓰고 앱의 메모리와 화면은 그대로 둔 채 새로 열기를 기다렸다. 한 번 새로 연 뒤에는 세션 표시가 다음 새로 열기를 막아, 받아도 화면에 안 보이거나 다음 저장이 옛 진도를 되살릴 수 있었다. 받은 직후 메모리와 화면을 함께 갱신한다.
- 앱으로 돌아올 때도 서버를 확인한다. 서버 자료가 깨져 있으면 빈 자료로 간주해 덮지 않고 오류를 알린다.
- `node tools/sync-test.js` 에 학습 직후 업로드, 동시 저장 충돌, 다시 앱을 볼 때 받기, 깨진 서버 사본 보존을 더해 확인했다. 실제 두 기기 계정 시험은 아직 하지 않았다.

## 보기를 「낱말 둘 × 조사 둘」로 짠다

- 앞서 같은 앞말을 1:2 로 고쳤지만, 정답 낱말이 여전히 **2:1:1** 로 남았다.
  많이 나온 쪽을 세면 낱말을 몰라도 절반은 맞았다
- 이제 낱말 둘과 조사 둘을 짝지어 넷을 만든다

  ```
  受付の(정답)   受付も
  改札の         改札も
  ```

  **요점은 반복을 없애는 것이 아니라 반복을 단서로 못 쓰게 하는 것이다.**
  낱말도 조사도 꼭 두 번씩 나오니 어느 쪽을 세어도 답이 드러나지 않고,
  **낱말과 조사를 둘 다 알아야** 풀린다
- 고른 조사는 **두 낱말 모두에 붙을 수 있어야** 한다. 한쪽에만 붙으면
  「来られますは」 같은 말이 생겨 그것만 지워도 답이 좁혀진다
- 실측 — 대상은 명사+조사 자리 **1,620개**(가릴 수 있는 4,579 중 35.4%)

  | | |
  |---|---|
  | 2×2 로 만들어짐 | **1,620 / 1,620 (100%)** |
  | 되채우기로 간 것 | 0 |
  | 보기가 넷 미만 | 0 |
  | 같은 앞말·같은 조사가 셋 이상 | 0 |

- 나머지 모양은 해당 없다 — 낱말 하나 52.1% · 서술이나 조사 둘 이상 10.4% ·
  수사+조수사 2.1%. 이쪽은 앞서 넣은 규칙들이 맡는다
- **보기를 6개로 늘리는 것은 미뤘다.** 재료는 3×2·2×3 모두 100% 나오므로
  할 수 있느냐가 아니라 **할 값어치가 있느냐**의 문제인데, 지금 그걸 판단할
  근거가 없다. 드는 값은 분명하다 — 폰에서 스크롤이 생기고, 3,000문장 ×
  3회차 내내 읽을 양이 1.5배가 된다. `BACKLOG.md` C-3 「무지한 응시자」로
  재고 정한다. 2×2 는 2×3 의 부분집합이라 지금 작업이 버려지지 않는다

## 진행 중인 단계를 고르면 풀던 자리에서 잇는다

- 단계 번호를 누르면 늘 첫 쪽으로 떨어졌다. 26번을 풀다 잠깐 딴 단계를
  보고 돌아오면 **1번부터 다시 찾아 내려가야** 했다
- 단계를 여는 길이 세 군데(왼쪽 목록·가로 내비·화살표 키)에 흩어져 각자
  `ST.lv=n; ST.pg=0` 을 적고 있었다. `goStage(n)` 하나로 모으고, 열고 난 뒤
  `resume()` 을 부른다 — 마지막으로 풀던 자리가 적혀 있으면 그 쪽으로 옮겨
  그 문장까지 굴려 준다
- 순서가 중요하다. `resume()` 은 **쪽 첫 문장이면 스크롤하지 않고** `true` 를
  돌려주므로, 먼저 맨 위로 올린 뒤에 불러야 한다
- **끝낸 단계는 그대로 첫 쪽에서 시작한다.** 회차를 마칠 때 `ST.at` 을 지우기
  때문이다. 따로 조건을 달지 않아도 저절로 갈린다
- 가나 표(`#lvKana`)와 「다음 단계」(회차를 다 마치고 넘어갈 때)는 그대로 뒀다.
  앞은 문장 단계가 아니고, 뒤는 처음 여는 단계라 첫 쪽이 맞다
- 확인 — 30번을 풀던 2단계 → 둘째 쪽 · 3번을 풀던 2단계 → 첫 쪽 ·
  손댄 적 없는 단계 → 첫 쪽 · 회차를 마쳐 자리가 지워진 단계 → 첫 쪽

  들어갈 때 온 자리를 `ST.rv` 에 적어 두고, 나갈 때 그리로 되돌린 뒤
  `resume()` 으로 풀던 문장을 되찾는다
- 오답노트 안에서 또 열어도 적어 둔 자리를 덮지 않는다. 덮으면 돌아갈
  곳이 오답노트 자신이 되어 영영 못 나간다
- `ST.rv` 는 `ST` 에 얹어 두어 **앱을 닫았다 열어도 살아 있다.**
  `encST` 는 항목을 하나씩 골라 담고 `mergeST` 는 모르는 항목을 그대로
  넘기므로, 진도 코드와 동기화에는 아무 영향이 없다
- 「단계로 돌아가기」(`#rvBack`)도 같은 길을 쓴다. 전에는 `ST.lv=1` 로
  **1단계 첫 쪽에 떨구고 있었다** — 5단계를 풀다 들어온 사람도 마찬가지였다
- 단계 번호를 눌러 옮길 때 첫 쪽으로 가는 것은 그대로 두었다.
  일부러 다른 단계를 고른 것이니 처음부터 보는 편이 맞다

## 최신화 뒤 「다른 기기 진도 받기」가 끝없이 돌던 것

바로 앞의 고침이 부른 되돌이다. 원인을 그대로 적어 둔다.

- 옛 퀴즈 키(`watashi|wa`)를 앞말로 접게 했는데 **이 기기에서만** 접었다.
  서버 사본에는 옛 키가 그대로 남아 있고, `mergeQuiz` 는 양쪽 키의
  **합집합**을 만든다. 그래서 합칠 때마다 옛 키가 되살아나 `changed` 가
  계속 섰다 — `put → push → 새로 열기 → 다시 접기 → 또 다름` 이 끝없이 돌았다
- **손보는 자를 하나로 모았다.** `cleanQuiz()` 를 `trainer.html` 에 두고
  동기화도 같은 함수를 쓴다(`tidy`). 합치기 전에 이 기기 것과 서버 것을
  **둘 다** 손본다. 한쪽만 손보면 반드시 또 어긋난다
- 손본 결과를 다시 손봐도 그대로여야 한다(**멱등**). 그 성질이 고리를 끊는다.
  시험으로 확인했다 — 두 번째 `changed` 가 `false`, 합친 것과 내 것이 같아진다
- 「ko:」로 시작하던 옛 키도 같은 함수로 모았다. 전에는 메모리에서만 지우고
  저장하지 않아, 같은 고리를 늦게 터뜨릴 씨앗이었다
- **새로 열기는 한 판에 한 번만** 한다(`jp3000-reloaded`). 합치기가 또
  어긋나도 앱이 열리자마자 다시 열리는 일에 갇히지 않는다.
  한 번 놓치는 편이 갇히는 것보다 낫다
- 교훈 — **기기 사이를 오가는 자료의 모양을 바꿀 때는, 한쪽만 바꾸면 안 된다.**
  합치기가 합집합이면 옛 모양은 반드시 되살아난다

  흰 선이라 아무것도 보이지 않았다. 판을 갈라야 했다

- **모든 팝업이 뒤를 흐린다.** 「더 배워보기」에서만 하던 것을 낱말
  팝업·설정·축하까지 넓혔다. **퀴즈는 뺀다** — 묻는 문장이 뒤에
  보여야 하기 때문이다
- 흐린 정도를 7px 에서 **3.5px** 로 절반 줄였다

**설명 갈래 이름을 46종 → 31종으로.** 같은 것을 다른 이름으로 부르는
곳이 많아 화면이 뒤죽박죽으로 보였다.

- 짝이 되는 말 → **짝** · 읽기, 읽기가 바뀌는 것 → **읽는 법**
- 같은 소리 → **뜻 구분** (早い/速い 와 같은 종류다)
- に와 차이·に와 구분·は와 구분·で와 구분·ています와 구분 → **쓰임 차이**
  - 「뜻 구분」에 넣지 않은 것은 그것이 「더 배워보기」에 늘 나오는
    갈래이기 때문이다. 조사는 어느 문장에나 있어 정작 봐야 할 낱말을
    밀어낸다
- 안내문 → 안내판 · 권유 → 권유 형태
- 막연한 이름을 합쳤다 — 다른 말 → 참고, 비교·경험 말하기 → 쓰임,
  정중형과 짝 → 짝, 확신의 세기 → 어감
- **날씨·번호·순서·입국심사 처럼 뜻이 분명한 이름은 그대로 두었다.**
  「짝」으로 뭉뚱그리면 오히려 무슨 표인지 알기 어려워진다
- `check.js` 가 갈래 목록을 찍는다. 한 번만 쓰인 이름이 늘면 알려 준다

## 지시어 설명을 한 양식으로

1-13 은 사전의 **짝 표**로 설명하는데 1-15 는 문장 주석에 **한 줄 글**로
같은 말을 적어 두었다. 한 무리에서 한 낱말만 표를 갖고 있었던 탓이다.
それ·あれ·そこ·あそこ 에는 표가 없어 문장 주석으로 때웠다.

- 네 무리를 모두 채웠다. 어느 낱말을 눌러도 같은 표가 나온다
  - 것: これ·それ·あれ·どれ
  - 곳: ここ·そこ·あそこ·どこ
  - 쪽: こちら·そちら·あちら·どちら
  - 수식: この·その·あの·どの
- 설명 칸(내 쪽 / 상대 쪽 / 둘 다에게서 멂)을 1-13 것으로 맞췄다.
  전에는 どれ·ここ·こちら 의 표가 설명 없이 비어 있었다
- 같은 말을 되풀이하던 문장 주석 다섯을 뗐다 — 1-15, 1-17, 1-21,
  1-31, 2-15. 사전 표가 그 자리에 나온다
- **「주의」 블록은 「더 배워보기」에 나오지 않는다.** `NPRIO` 에 든
  갈래(짝·반대말·뜻 구분 …)만 나오고, 나머지는 낱말을 눌러야 보인다.
  그래서 주석을 떼려면 그 낱말에 **짝 표**가 있어야 한다

## 앱이 옛 화면에 갇혀 있던 진짜 이유

며칠째 새 판이 폰에 반영되지 않았다. 껐다 켜도, 브라우저를 바꿔도
그대로였다. 원인은 둘이 겹친 것이었다.

**하나. 뒤에서 받아 두는 일을 `waitUntil` 로 붙잡지 않았다.**
`sw.js` 는 저장해 둔 것을 먼저 내주고 뒤에서 새것을 받아 캐시를
갱신하도록 되어 있었다. 그런데 저장해 둔 것이 있으면 `respondWith` 가
곧바로 끝나고, **그 순간 iOS 는 서비스 워커를 재워버린다.**
그래서 `cache.put` 이 영영 실행되지 않았다. PC 에서는 워커가 더 오래
살아 있어 드러나지 않았다.

**둘. `sw.js` 자체가 9월 7일 뒤로 바뀌지 않았다.**
브라우저는 이 파일의 내용이 달라져야 서비스 워커를 새로 깐다.
`jp3000.html` 만 여러 번 바뀌고 `sw.js` 는 그대로였으니, 새로 깔 일도
없었고 뼈대를 다시 받을 일도 없었다. 앱이 그 시점에 얼어붙었다.

고친 것

- 뒤에서 받는 일을 `e.waitUntil()` 로 붙잡는다
- `build.py` 가 만들 때마다 `sw.js` 의 `BUILD` 줄에 판을 찍는다.
  파일 내용이 늘 바뀌므로 브라우저가 서비스 워커를 새로 깔고,
  그때 뼈대를 다시 받는다. 캐시 이름도 판을 따라 바뀌어 옛것은 지워진다
- `tools/sw-test.js` — 서비스 워커를 흉내 낸 환경에서 돌려,
  저장해 둔 것이 있어도 캐시가 갱신되는지 본다.
  옛 `sw.js` 로 돌리면 실패한다

## 옛 화면에서 벗어나지 못할 때 쓰는 fix.html

앱이 며칠째 옛 화면만 내놓는 일이 있었다. 앱을 껐다 켜도, 브라우저를
바꿔도 그대로였다.

- 원인은 **주소 뒤에 무엇을 붙여도 소용없다는 것.** `sw.js` 의
  `cache.match(req,{ignoreSearch:true})` 가 물음표 뒤를 무시하고
  저장해 둔 것을 그대로 내준다. `?v=1` 로 캐시를 지나치려던 것이
  통하지 않았던 까닭이다
- 사파리에도 서비스 워커가 등록돼 있어 브라우저를 바꿔도 같았다
- **`fix.html` 을 저장소 뿌리에 두었다.** 서비스 워커는 `dist/` 안에서만
  도므로 그 바깥에 있는 이 파일은 가로채이지 않는다. 열면 서비스 워커를

## 오답노트 두 번 맞히기 · 회차 끝 바로가기 · 팝업 뒤 흐리기

- **오답노트는 한 말을 두 번 맞혀야 끝난다.** 첫 번째는 뜻을,
  두 번째는 일본어를 묻는다. 한 번 맞힌 것은 뒤로 돌려 두었다가
  다시 내고, 틀리면 처음으로 돌아가 두 번을 새로 채운다.
  간격 반복(3일·1주·3주)은 두 번을 다 채웠을 때만 한 칸 나아간다 —
  전에는 답할 때마다 나아갔다
- 진행 표시는 **끝낸 말의 수**를 센다. 같은 말을 두 번 물어도
  하나로 센다
- **세 회차를 다 돌았을 때 오답노트에 쌓인 것이 있으면** 축하 팝업의
  마지막 줄 아래에 「오답노트 N개」를 띄운다. 여기서 놓치면 한참
  뒤에야 다시 눈에 띈다. 별이 왕관에 앉은 뒤 옮겨 간다
- **「더 배워보기」 팝업은 뒤를 흐린다.** 읽을 것이 많아 뒤가 비치면
  눈이 흩어진다. 그 팝업에서만 흐리고 다른 팝업은 그대로다

## 마지막에 보던 자리에서 잇기

앱을 껐다 켜면 단계와 쪽은 되찾았지만 늘 쪽 맨 위에서 다시 시작했다.
25문장짜리 쪽 한복판에서 그만두었으면 매번 찾아 내려가야 했다.

- 앱을 열면 그 문장으로 간다. 쪽이 어긋나 있으면 쪽부터 맞춘다.
  쪽의 첫 문장이면 굳이 옮기지 않고 위에서 시작한다

- 회차를 마치면 적어 둔 자리를 지운다. 새 회차는 처음부터다

  합칠 수 없으니 이 기기 것을 남기고, 이 기기에 없는 단계만 받는다
- 한 쪽에 몇 문장인지(25)가 세 군데에 흩어져 있어 `PG` 하나로 모았다

## 겉모습이 닮은 보기까지 걸러냄

- 한자가 똑같은 것(何 / 何)만 걸렀는데, **「何」와 「何か」처럼 가나 한둘만
  더 붙은 것**도 화면에서는 같은 낱말이 두 번 나온 것으로 읽힌다.
  한쪽이 다른 쪽의 앞머리이고 남는 것이 가나뿐이면 함께 내놓지 않는다.
  三人·日本人처럼 한자가 더 붙은 것은 눈에 뚜렷이 달라 그대로 둔다
- 다만 **「十番」과 「十番の」처럼 조사만 다른 것은 걸러선 안 된다.**
  조사가 붙는지를 묻는 것이 그 문제의 요지다. 검사기는 앞부분의 낱말이
  같으면 조사 차이로 보고 넘어간다
- 닮은 것을 견주는 일은 점수가 높은 위쪽 60개에서만 한다. 후보 전체를
  서로 견주게 했더니 검사가 끝나지 않았다. 그때 후보 꼬리를 잘라 냈다가
  보기가 하나뿐인 문제가 254건 생기기도 했다 — 겹침만 보고 후보는
  살려 두어야 한다
- `src/quiz.js` 에 NUL 바이트가 하나 들어가 있어 파일이 이진 파일로
  다뤄지고 있었다. 지웠다

## 퀴즈 보기 손질

말이 안 되는 보기가 여럿 나가 있었다. 고치기 전에 먼저 **검사기**를
만들었다. 3,000문장의 보기를 사람이 눈으로 볼 수 없기 때문이다.

- 보기를 만드는 코드를 `src/quiz.js` 로 떼어 냈다. 화면을 건드리지
  않는 순수한 코드만 두어, 브라우저 없이 그대로 돌려 볼 수 있다
- `tools/quiz-audit.js` — 모든 문장의 모든 자리에서 보기를 만들어
  본다. 겹치는 보기·이상한 말·잘린 말·있을 수 없는 말·정답 없음을 본다

고친 것 (처음 검사에서 309건)

- **어미가 겹쳤다.** 「실례하겠습니다」의 어간을 「실례하겠」으로 잘라
  거기에 어미를 또 붙여 「실례하겠겠습니다」·「실례하겠을 겁니다」를
  만들었다. 겠·았·었이 이미 붙은 말을 먼저 걸러 내고, 만든 뒤에도
  이상한 꼴은 버린다. 「았」과 「었」은 앞 소리를 보고 고른다
- **겉모습이 같은 보기.** 何(なん)과 何(なに)는 화면에서 구별되지
  않는다. 한자가 같은 것은 하나만 남긴다
- **품사가 다른 보기.** 「내일은 [근무]입니다」의 보기로 「봐도」·「도와」
  같은 동사꼴이 나왔다. 뜻갈래에서 고를 때 품사를 함께 본다
- **정답과 뜻이 같은 보기.** 仕事의 뜻이 「일, 업무」인데 정답이 「근무」면
  「업무」도 맞는 답이다. 명사 자리에서는 뜻이 같은 말을 오답으로
  쓰지 않는다. 서술 자리의 「있습니다 / 있습니까」는 어미가 다르므로
  그대로 둔다 — 그것이 물어야 할 바다
- **있을 수 없는 말.** 서술 뒤에 격조사를 붙여 「ですは」·「来られますは」가
  나왔다. から·が 는 서술 뒤에 정상이므로 그대로 둔다
- **잘린 말.** 「됩니」·「있었습니」가 보기로 나왔다. 끝이 「니」인데 앞
  글자 받침이 ㅂ이면 잘린 것으로 본다 (어머니·언니는 걸리지 않는다)
- 1단계 11번의 「입어」가 명사로 표시돼 있었다. 동사꼴이라 `v` 로 고쳤다

## 시험용 진도 채우기를 지움

- 회차 완료 연출을 보려고 넣어 둔 블록이 배포본에 그대로 남아 있었다.
  `jp3000-seed` 값이 없는 **모든 새 방문자**에게 조건이 참이 되어,
  링크를 처음 여는 사람마다 1단계가 3회차까지 채워지고 별 두 개가
  붙은 상태로 시작했다. 주석에 「확인이 끝나면 이 블록을 지운다」고
  적어 두었는데 지우지 않았다
- **전체 초기화가 서버 사본도 지우게 했다.** 지우지 않으면 다음에
  맞출 때 지운 진도가 그대로 되살아난다. 합치기는 양쪽을 다 살리는
  쪽이라, 한쪽만 비워서는 비워지지 않는다.
  기기마다 사본이 있으므로 쓰는 기기 모두에서 초기화해야 깨끗해진다

## 기기 간 진도 동기화

- 설정에 「기기 간 동기화」를 넣었다. 이메일·비밀번호로 로그인하면
  폰과 PC의 진도가 자동으로 맞춰진다. Firebase 를 쓴다
- **SDK 를 쓰지 않고 REST 로 부른다.** 합본 HTML 하나로 도는 성질을
  지키기 위해서다. 밖에서 받아 오는 파일이 하나도 없다
- 구글 로그인이 아니라 이메일·비밀번호다. 홈 화면에 설치한 앱은
  아이폰에서 사파리와 저장 공간이 나뉘어 있어, 밖에 나갔다 오는
  로그인 방식은 결과가 앱 안으로 들어오지 못한다
- **합치는 규칙.** 진도는 늘어나기만 하는 자료라 양쪽을 다 살릴 수 있다
  - 맞힌 자리(`QDONE`)는 값이 회차 비트라 OR 하면 그대로 합쳐진다
  - 완료 문장은 합집합, 단계·회차·별은 큰 쪽
  - 맞힘·틀림 횟수는 큰 쪽. 더하면 부풀고 한쪽만 두면 사라진다
  - 북마크는 단계마다 한 자리뿐이라 합칠 수 없다. 이 기기 것을 남긴다
- **공부하는 중에는 올리기만 한다.** 내려받아 합치면 화면을 새로 열어야
  하는데 문제를 푸는 중에 그러면 안 된다. 받는 것은 앱을 열 때와
  「지금 맞추기」를 눌렀을 때뿐이다
- 화면 설정(글씨·소리·목소리)은 기기마다 다른 게 자연스러워 옮기지 않는다
- **코드 복사·붙여넣기는 그대로 둔다.** 서버가 죽었을 때의 탈출구다
- `node tools/sync-test.js` — 두 기기를 흉내내어 합치기를 검사한다.
  합치는 규칙을 손대면 반드시 돌린다

## 회차 학습 · 4단계 (회차를 마쳤을 때)

- 회차를 마치면 축하 팝업이 뜬다. 큰 별이 튀어오르고, 얻은 별 개수와
  다음 회차가 무엇을 가리는지 알려 준다
- 색종이. 라이브러리 없이 캔버스에 직접 그린다. 조각 90개, 약 2.6초.
  색은 앱 팔레트 그대로 — 금색·초록·연초록·크림
- 축하음. 이미 있던 `tone()` 으로 4음 아르페지오. 효과음이 「없음」이면 안 난다
- 팝업을 닫으면 **별이 위쪽 왕관 자리로 날아가 박힌다.**
  날아오기 전까지 그 자리는 비워 두었다가(`data-hold`), 착지하면 채우고 한 번 튄다
- 별 채우는 차례를 왼쪽 → 오른쪽 → 가운데로 바꿨다.
  가운데가 가장 높이 솟아 있어 마지막에 채워야 왕관이 완성돼 보인다.
  PC 세로 목록은 한 줄이라 `order` 로 자리를 바꿔 왼쪽부터 차 보이게 했다
- 「움직임 줄이기」를 켠 기기에서는 색종이와 날아가는 별을 건너뛰고
  팝업만 조용히 띄운다. 별은 그대로 채워진다

## 회차 학습 · 3단계 (별과 손질)

- 단계 동그라미 위에 별 세 개를 왕관처럼 얹었다.
  기본은 빈 별 세 개이고, 회차를 마칠 때마다 왼쪽부터 금색으로 찬다
  - 가로 내비는 `overflow-x` 때문에 위로 삐져나온 것이 잘린다.
    `.levels` 의 위쪽 여백을 16px 로 늘려 그 안쪽에 별을 그린다
  - 유니코드 ★ 는 기기마다 모양이 달라 SVG 로 그렸다
  - PC 왼쪽 세로 목록에는 글줄 옆에 나란히 붙인다
- 완료 표시를 「완료」 글자에서 초록 동그라미 체크로 바꿨다

  팝업을 화면 가운데로 옮겼다. 쓰지 않던 `.tbody2` CSS 를 지웠다

## 회차 학습 · 2단계 (회차 판정과 교차 가림)

- 한 단계를 세 번 돈다. 머리띠에 「1회차」가 금색으로 뜬다
  - 1회차 한국어를 가린다 · 2회차 좌우를 번갈아 가린다 · 3회차 일본어를 가린다
- 2회차 교차는 좌우 덩어리 수가 같은 1,471문장에서 한다.
  수가 다른 79문장은 한쪽만 통짜로 가린다.
  짝을 모르는 채 교차하면 가린 자리의 단서까지 같이 가려져 풀 수가 없다
- 어느 쪽부터 가릴지는 문장 번호로 정한다. 다시 열어도 같은 자리가 가려진다
- **완료는 손으로 하지 않는다.** 그 문장의 가린 자리를 다 맞히면 완료가 된다
- 단계를 다 채우면 별이 하나 붙고 다음 회차로 넘어간다.
  별은 「다시 풀기」로도 지워지지 않는다
- 왼쪽으로 밀어 완료하던 것을 뺐다. 오른쪽으로 미는 북마크는 그대로다
- 보기 모드 단추(눈 아이콘)를 감췄다. 코드는 남겨 두었고,
  CSS 한 줄(`#bEye{display:none}`)을 지우면 「모두 보기」가 가림 끄기가 된다

## 회차 학습 · 1단계 (저장 구조와 덩어리 나누기)

**덩어리 나누기를 고쳤다** — 좌우 짝이 맞는 문장 84.3% → 94.9%

- 단위는 앞이 숫자일 때만 앞말에 붙인다.
  「本」이 단위(자루)와 명사(책)를 겸해서 「かばんに / 本が」가 뭉쳐 있었다.
  한국어 「개」도 같은 이유로 「공원에 / 개가」가 뭉쳤다
- `GLUEJP` 에서 ています·ていただけますか 계열 13개를 뺐다.
  한국어가 「말해 / 주시겠습니까」 두 덩어리인데 일본어만 한 덩어리였다. 164문장
- 28-11 이 「3」 대신 「씨」 키를 쓰고 있었다 (`san` → `san3`)
- 남은 79문장은 문장 데이터 쪽 문제라 전수 검토로 미룬다

**저장 구조** — 회차를 담을 수 있게 바꿨다. 화면에는 아직 안 나온다

- 맞힌 자리(`QDONE`)의 값을 회차 비트로. 1회차=1, 2회차=2, 3회차=4
- 완료 문장을 회차별로 세 벌 (`ST.done[회차][단계]`)
- 별(`ST.star`)과 현재 회차(`ST.r`)를 따로 저장.
  별은 「다시 풀기」로도 지워지지 않아야 하므로 계산으로 뽑지 않는다
- 진도 코드 `J2` → `J3`, 퀴즈 코드 `Q1` → `Q2`. 옛 코드는 그대로 읽힌다
- 옛 진도는 1회차 완료분으로 옮기고, 다 끝낸 단계에는 별 하나를 준다
- 「이 단계 다시 풀기」는 지금 도는 회차만 되돌린다

## 다크 모드

- 설정 첫 항목에 「화면」 추가 — 기기 설정 / 밝게 / 어둡게
- 「기기 설정」은 폰·PC의 다크 모드를 따라가고, 도중에 바뀌면 같이 바뀐다
- CSS에 직접 박혀 있던 색 51군데를 변수로 끌어올렸다.
  어두운 판은 `:root[data-theme="dark"]` 한 곳에서만 값을 갈아 끼운다
- 칠하는 초록(`--green`)과 글자로 쓰는 초록(`--acc`)을 갈랐다.
  어두운 판에서는 글자 쪽만 밝아진다. 벽돌색도 `--seal` / `--acc-r` 로 같은 방식
- 머리띠와 팝업(`--band`)은 두 판 모두 짙은 초록 그대로 둔다
