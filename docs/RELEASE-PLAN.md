## 1. 어디까지 되어야 「정식 앱」인가

목표 모습은 단순히 지금 웹페이지를 앱스토어에 싸서 올리는 것이 아니다.
아래가 한 제품으로 이어져야 한다.

| 갈래 | 출시할 때의 상태 |
|---|---|
| 교재 | 60단계·3,000문장과 사전·설명·퀴즈 검수 완료 |
| 학습 | 3회차·오답노트·진도 동기화가 기기 변경과 앱 갱신에도 안전함 |
| 회화 | 학습 범위를 아는 AI와 글 또는 음성으로 상황별 대화 |
| 소리 | 문장 음성의 포맷·저장·오프라인 받기 정책 확정 |
| 제품 얼굴 | 이름·로고·앱 아이콘·첫 화면·빈 화면·오류 화면까지 한 체계 |
| 계정 | 가입·로그인·복구·로그아웃·내보내기·탈퇴가 모두 있음 |
| 운영 | 문의 접수, 장애 확인, 공지, 환불·복구 대응 창구가 있음 |
| 유료 기능 | 결제보다 먼저 권한·갱신·취소·환불·복원까지 한 흐름으로 동작 |
| 배포 | 개발·시험·운영 환경이 갈리고, 자동 검사·배포·되돌리기가 가능함 |
| 법과 정책 | 개인정보·이용약관·AI 안내·스토어 표기와 계정 삭제 요건을 충족 |

### 끝까지 지킬 성격

- **교재의 중심은 3,000문장이다.** AI가 교재를 대신하거나 진도를 결정하지 않는다
- **핵심 학습은 오프라인에서도 된다.** 인터넷·로그인·결제 장애가 문장 학습을 막지 않는다
- **진도를 볼모로 잡지 않는다.** 내보내기와 기기 안 사본을 유지한다
- **AI·결제 같은 온라인 기능만 서버에 의존한다.** 안 될 때 이유와 돌아갈 길을 보여준다
- **한 번에 갈아엎지 않는다.** 작동하는 기능을 경계별로 떼어 내며 옮긴다

## 2. 코드를 바꾸기 전에 결정할 것

아래는 아직 결정이 아니다. **추천 출발점**일 뿐이며, 0단계에서 하나씩 확정한다.

| 질문 | 추천 출발점 | 이유 |
|---|---|---|
| 어디에 출시하나 | 웹/PWA 유지 + iOS·Android 동시 준비 | 기존 사용자를 버리지 않고 스토어를 넓힌다 |
| 네이티브 앱을 새로 쓰나 | 먼저 Capacitor로 감싸고 부족한 부분만 네이티브로 | 검증된 웹 학습 화면을 다시 만들 위험을 줄인다 |
| 무엇을 유료로 하나 | 3,000문장 핵심은 무료, 사용량 비용이 드는 AI 회화를 유료 후보로 | 기존 「학습을 볼모로 잡지 않는다」와 비용 구조를 함께 지킨다 |
| AI 회화의 첫 형태 | 글 대화 먼저, 실시간 음성은 그다음 | 수준 조절과 교정 품질을 먼저 검증할 수 있다 |
| 계정은 필수인가 | 오프라인 교재는 선택, 동기화·AI·결제는 필수 | 무료 학습의 문턱은 그대로 두고 온라인 남용과 구매 복원을 막는다 |
| 대화를 저장하나 | 원문은 기본 저장 안 함, 사용자가 동의한 요약만 저장 | 민감한 여행·건강 표현이 섞일 수 있고 보관 비용도 든다 |
| 첫 시장은 어디인가 | 한국어 사용자·한국 스토어부터 | 지금 교재와 설명이 한국어 화자 전용이다 |
| 구독인가 이용권인가 | AI 원가를 실측한 뒤 결정 | 가격부터 정하면 사용량이 많은 사람에게 적자가 날 수 있다 |

### 0단계에서 숫자로 답할 것

- 한 번의 글 회화와 10분 음성 회화에 드는 실제 비용
- 한 사용자가 하루·한 달에 회화를 몇 번 쓰는지
- 3,000문장·압축 음성·앱 껍데기의 최종 설치 및 내려받기 크기
- 현재 지원 가능한 문의량과 환불 처리량
- 무료/유료 경계를 달리한 시제품의 사용 결과

재기 전에는 가격·무제한 제공·출시일을 정하지 않는다.

## 3. 지금 구조에서 무엇이 임시인가

현재 구조는 교재 시제품으로는 단순하고 강하다. 문제는 사용자가 늘고 결제와
AI가 붙으면 **서버가 책임져야 할 상태까지 브라우저가 맡고 있다는 것**이다.

| 지금 | 정식 구조 | 옮기는 까닭 |
|---|---|---|
| `trainer.html` 한 파일에 화면·상태·기능 | 소스는 기능별 모듈, 배포본은 다시 묶어도 됨 | 고침과 시험의 경계를 만든다 |
| GitHub Pages에 수동 푸시 | 시험 주소 + 운영 주소 + 자동 배포·되돌리기 | 운영판을 직접 시험장으로 쓰지 않는다 |
| 한 Firebase 프로젝트 | 개발·시험·운영 프로젝트 분리 | 시험 데이터와 실제 사용자를 섞지 않는다 |
| `localStorage`가 진도의 중심 | 기기 안 사본 + 버전 있는 서버 사본 | 오프라인과 기기 복구를 함께 지킨다 |
| `sync.js`가 REST 병합까지 맡음 | 동기화 계약·저장소·화면을 분리 | 자료 모양을 바꿔도 화면을 덜 건드린다 |
| API 키를 로컬 파일에서 빌드 도구만 사용 | 런타임 비밀은 Secret Manager 또는 보호된 AI 게이트웨이 | 공개 앱에 장기 키를 넣지 않는다 |
| 서비스 워커를 직접 판 찍어 갱신 | 버전 배포·점진 공개·되돌리기와 캐시 이관 시험 | `fix.html`이 필요한 사고를 출시 전에 잡는다 |
| WAV를 저장소 밖에 둠 | 압축 파일 + 단계별 내려받기 + 용량 관리 | 전체 음성을 앱 설치와 함께 받지 않는다 |
| 결제 권한 없음 | 서버의 `entitlement`가 유료 권한의 원본 | 로컬 값을 고쳐 유료 기능을 여는 일을 막는다 |
| 문의 창구 없음 | 앱 안 문의 + 운영자 대기열 + 답변 이력 | 오류·환불·콘텐츠 신고를 잃지 않는다 |
| 수동 검사 후 직접 푸시 | CI에서 검사 후 시험 배포, 승인 뒤 운영 배포 | 검사하지 않은 배포를 막는다 |

**단일 배포 파일 자체는 버릴 대상이 아니다.** 소스까지 한 파일인 것이 문제다.
소스는 나누고 빌드 결과를 적게 유지하면 오프라인 장점은 그대로 가져갈 수 있다.

## 4. 추천하는 목표 구조

```text
                         ┌─ 웹/PWA
소스 모듈 → 공통 웹앱 ──┼─ iOS 껍데기(Capacitor 후보)
                         └─ Android 껍데기(Capacitor 후보)
                              │
          ┌───────────────────┼───────────────────┐
          │                   │                   │
    기기 안 학습 자료     Firebase Auth       App Check
    진도·오프라인 음성         │                   │
          │                   └─────────┬─────────┘
          │                             │
          │                  Firebase AI Logic 또는 API
          │                  ├─ 수준별 글 회화
          │                  └─ Live API 음성 회화
          │                             │
          └────────── Firestore ────────┤
                       진도·설정         │
                       문의·사용량       │
                       유료 권한         │
                                        │
                 Cloud Functions/Run ───┘
                 ├─ 결제 검증·웹훅
                 ├─ 계정 삭제·자료 내보내기
                 ├─ 사용량 제한·운영 작업
                 └─ 필요한 경우 Live API 임시 토큰
```

### 앞단

- `src/`를 화면, 학습 상태, 퀴즈, 동기화, 회화, 결제로 나눈다
- 빌드 도구를 두어 브라우저용과 스토어용에서 같은 학습 코드를 쓴다
- 상태 읽기·쓰기를 한 인터페이스 뒤로 숨긴다. 처음에는 `localStorage`, 이후
  필요하면 IndexedDB나 네이티브 저장소로 바꿔도 학습 코드는 그대로 둔다
- iOS·Android는 기존 웹앱을 감싸는 방식부터 검증한다. 다만 단순한 웹사이트
  포장으로 보이지 않도록 오프라인 학습·음성·복원·설정까지 앱 안에서 완결한다

### 서버

- 기존 Firebase를 활용하되 **개발·시험·운영을 별도 프로젝트**로 둔다
- 정적 앞단은 Firebase Hosting을 우선 후보로 둔다. 미리보기 주소와 되돌리기가
  있어 GitHub Pages보다 운영 배포를 나누기 쉽다
- 짧고 단순한 작업은 Cloud Functions, 결제·AI 중계처럼 복잡해지면 Cloud Run을 본다
- Gemini·결제 키와 웹훅 비밀은 Secret Manager에 둔다
- Firestore 규칙, App Check, 인증을 각각 켠다. Firebase 설정값이 보인다는 이유로
  보안을 맡기지 않고 **규칙과 검증**으로 접근을 막는다

### 자료의 원본

| 자료 | 원본 | 기기에는 |
|---|---|---|
| 3,000문장·사전 | 앱 배포본 | 전부 또는 단계별 묶음 |
| 학습 진도 | 서버와 기기 사본을 병합 | 오프라인 학습을 위해 유지 |
| 유료 권한 | 서버 | 만료 시간이 있는 짧은 사본 |
| 결제 거래 | 스토어/결제사 + 서버 검증 결과 | 영수증 원문을 오래 두지 않음 |
| AI 사용량 | 서버 | 화면 표시용 요약 |
| 회화 원문 | 기본은 저장하지 않음 | 현재 세션 동안만 |
| 문의 | 서버 | 보낸 내역을 읽기 위한 사본 |

자료 모양에는 모두 `version`을 둔다. 앱을 올릴 때 **이전 두 판 이상에서 새 판으로
옮기는 시험**을 자동으로 돌린다. 진도와 구매 권한은 초기화로 고칠 수 있는 자료가 아니다.

## 5. 분야별 작업

### A. 교재와 음성

1. 32~60단계 1,450문장을 작성한다
2. 3단계마다 지금의 전수 검토를 계속한다
3. 3,000문장 완성 뒤 원어민에게 표본이 아니라 위험군 중심 검수를 맡긴다
4. 퀴즈·덩어리·설명 검사기를 CI에서 매번 돌린다
5. 음성을 Opus/AAC 등 실제 대상 기기에서 비교하고 포맷을 고른다
6. 단계별 음성 받기·지우기·다시 받기와 남은 용량 표시를 만든다
7. 음성이 없거나 인터넷이 끊긴 경우 브라우저/기기 음성으로 돌아간다

**완료 기준** — 문장·퀴즈 검사 0건, 정한 원어민 검수 표본 처리 완료,
지원 기기에서 음성 받기·삭제·오프라인 재생이 모두 된다.

### B. 앱 코드와 배포 기반

1. 상태 저장, 문장 렌더링, 퀴즈, 음성, 동기화를 모듈로 나눈다
2. `src → web bundle → iOS/Android assets` 빌드 흐름을 하나로 만든다
3. 지금의 `check.js`, `quiz-audit.js`, `sync-test.js`, `sw-test.js`를 CI에 연결한다
4. 변경마다 시험 주소를 만들고, 운영은 승인된 태그만 배포한다
5. 캐시 이관·진도 이관·되돌리기 시험을 추가한다
6. 오류 수집에는 비밀번호·대화 원문·진도 코드가 들어가지 않게 거른다

**완료 기준** — 새 컴퓨터에서 문서에 적힌 한 흐름으로 세 대상 빌드를 만들고,
운영 자료를 쓰지 않는 시험 환경에서 설치·갱신·되돌리기를 재현한다.

### C. 계정과 동기화

1. 이메일 확인, 비밀번호 재설정, 로그인 기기 확인을 갖춘다
2. 비로그인 진도를 가입 뒤 안전하게 합치는 규칙을 정한다
3. 동기화 충돌 규칙을 자료별로 문서화하고 시험한다
4. 내 자료 내보내기와 **앱 안 계정 삭제**를 만든다
5. 탈퇴 시 인증, 진도, 문의, AI 요약을 지우고 법적으로 보관해야 하는 결제 기록만 분리한다
6. 서버 장애 때 기기 진도를 보존하고 복구 뒤 다시 합친다

**완료 기준** — 새 가입, 기존 계정, 비밀번호 분실, 두 기기 충돌, 탈퇴 후 재가입을
각각 자동·수동으로 시험하고 다른 사용자의 자료가 섞이지 않는다.

### D. AI 회화

#### 1차: 글 회화

1. `ST.lv` 하나가 아니라 `done`·`star`·`r`·`QSTAT`을 함께 읽어 학습 프로필을 만든다
2. 실제로 공부한 단계의 문형, 자주 틀린 낱말, 선택한 여행 장면만 짧게 보낸다
3. Gemini는 한 번에 1~2문장으로 말하고, 배운 범위를 우선하며 새 표현을 제한한다
4. 응답을 `reply`, `correction`, `hintKo`, `newExpression` 같은 구조화 자료로 받는다
5. 화면에는 HTML을 그대로 넣지 않고 각 값을 검사한 뒤 글자로 넣는다
6. 틀린 표현을 오답노트에 넣을 때는 사용자가 확인하게 한다
7. 단계별 대표 대화와 고의 오류로 고정 평가 세트를 만든다

#### 2차: 실시간 음성

1. 글 회화의 수준 조절과 교정이 먼저 통과한 뒤 시작한다
2. Live API의 음성 입력·출력, 중간 끊기, 다시 연결, 세션 요약을 시제품으로 잰다
3. 원 API를 브라우저에서 바로 쓸 경우 서버가 짧게 사는 임시 토큰을 발급한다
4. Preview 기능이 바뀌거나 멈춰도 글 회화로 돌아갈 수 있게 한다
5. 녹음 시작·전송 중·종료를 분명히 표시하고, 마이크 권한을 거절해도 앱이 동작하게 한다

#### 보호와 비용

- Gemini 장기 키를 HTML·JavaScript·앱 꾸러미에 넣지 않는다
- Firebase AI Logic을 쓰면 App Check와 인증 사용자 제한을 강제한다
- 사람의 대화 속도에 맞게 사용자별 요청 제한을 낮추고 일일 한도와 전체 중지 스위치를 둔다
- 안정판 모델 이름을 고정하고 Remote Config 또는 서버 프롬프트로 바꿀 수 있게 한다
- 대화 원문은 기본 저장하지 않는다. 품질 개선용 전송은 따로 동의를 받는다
- 사용자에게 AI 답변이 틀릴 수 있고 사람 상담이 아니라는 점을 밝힌다

**완료 기준** — 단계별 평가에서 범위를 넘는 문법·지나친 장문·잘못된 교정 사례를
사람이 확인하고 기준을 세운 뒤 그 기준을 통과한다. 비용과 지연 시간은 실제 사용량으로 잰다.

### E. 이름·로고·화면·연출

1. 앱 이름과 상표·도메인 사용 가능 여부를 먼저 확인한다
2. 로고보다 먼저 브랜드 키워드와 금지할 인상을 정한다
3. 앱 아이콘은 작은 크기, 밝은/어두운 바탕, iOS·Android 마스크에서 확인한다
4. 첫 화면은 「바로 이어서 학습」을 중심에 두고 로그인·구매를 앞세우지 않는다
5. 색·글자·간격·모서리·그림자·움직임을 디자인 토큰으로 만든다
6. 로딩·빈 상태·오프라인·권한 거절·결제 실패·AI 한도 초과 화면도 함께 디자인한다
7. 움직임 줄이기, 글자 확대, 화면 읽기, 색 대비, 키보드 조작을 시험한다
8. 연출은 학습 완료를 설명하는 데 쓰고 정답을 늦추거나 반복을 강요하지 않는다

**완료 기준** — 로고 파일 하나가 아니라 아이콘 세트, 시작 화면, 핵심 화면,
오류·빈 상태와 사용 규칙까지 한 묶음으로 남는다.

### F. 문의와 운영

1. 설정에 「문의하기」를 두고 오류·내용 신고·결제·계정·기타로 나눈다
2. 앱 판, 운영체제, 단계·문장 번호는 미리 채우되 사용자가 보고 뺄 수 있게 한다
3. 대화 원문·진도 전체·개인정보는 자동 첨부하지 않는다
4. 문의에 접수 번호와 상태를 붙이고 같은 답을 다시 찾을 수 있게 한다
5. 앱을 열 수 없을 때 쓸 공개 지원 페이지와 지원 전용 주소를 둔다
6. 장애·공지·환불·콘텐츠 수정의 담당 절차와 답변 기준을 정한다
7. 자주 묻는 문제는 도움말로 옮기고 앱 판별·캐시 복구 절차를 최신으로 유지한다

**완료 기준** — 로그인 불가, 결제 복원, 잘못된 문장, AI 오답, 앱 실행 불가를
각각 접수해 담당자가 필요한 정보만으로 처리할 수 있다.

### G. 유료 플랜과 결제

1. 먼저 유료 권한을 `plan`, `status`, `expiresAt`, `source`, `productId`로 정의한다
2. 웹·Apple·Google 결제를 같은 권한으로 바꾸는 서버 계층을 만든다
3. iOS 디지털 기능은 StoreKit, Play 배포판은 Play Billing을 기본 경로로 본다
4. 웹 결제사는 나중에 고르되 성공 화면이 아니라 **서버 웹훅 검증 뒤** 권한을 준다
5. 구매·갱신·유예·보류·취소·환불·회수·복원 상태를 모두 시험한다
6. 웹훅은 같은 알림이 여러 번 와도 결과가 한 번만 반영되게 만든다
7. 앱 삭제·기기 변경·재가입 뒤에도 구매 복원이 된다
8. 가격에는 Gemini 사용료, 스토어 수수료, 세금, 환불, 지원 비용을 함께 넣는다
9. 무료 체험과 무제한 표시는 비용 상한과 악용 방지 수단을 만든 뒤에만 쓴다

**절대 하지 않는 것** — `localStorage.isPaid=true` 같은 값을 유료 권한으로 믿기,
클라이언트의 구매 성공 콜백만 보고 권한 주기, 웹훅 없이 구독 만료를 추측하기.

### H. 개인정보·보안·스토어 정책

1. 수집 자료 지도를 만든다: 이메일, 진도, 문의, 결제 식별자, AI 입력·출력, 진단 정보
2. 자료마다 목적, 보관 기간, 삭제 방법, 제3자 전송처를 적는다
3. 개인정보 처리방침·이용약관·유료 서비스와 환불 안내·AI 기능 안내를 준비한다
4. Apple App Privacy와 Google Play Data safety 답변을 실제 코드와 맞춘다
5. 계정 생성이 있으면 앱 안과 공개 웹 양쪽에서 삭제를 시작할 수 있게 한다
6. Firestore 규칙, App Check, 키 제한, 최소 권한, 관리자 접근 기록을 점검한다
7. 의존성 목록과 라이선스, 취약점 검사를 관리한다
8. 어린이 대상 여부, 한국 외 출시 지역의 결제·개인정보 요건을 출시 직전에 다시 확인한다

정책은 바뀐다. 아래 참고 링크는 출발점일 뿐이며 **스토어 제출 직전에 원문을 다시 읽는다.**

### I. 스토어 앱과 출시 운영

1. Capacitor 시제품으로 설치, 오프라인, 키보드, 음성, 공유, 앱 복귀를 확인한다
2. 필요할 때만 네이티브 플러그인을 붙인다: 결제, 안전한 저장소, 햅틱, 알림, 마이크
3. 패키지 이름, 서명 키, 앱 ID, Universal/App Links를 운영 자산으로 보관한다
4. 앱 아이콘, 시작 화면, 설명, 검색어, 스크린샷, 개인정보 URL, 지원 URL을 준비한다
5. 내부 시험 → 닫힌 시험 → 공개 시험 순서로 실제 기기 자료를 모은다
6. 스토어 심사 계정과 AI·결제 기능을 재현하는 설명을 심사 메모에 적는다
7. 출시 비율을 나눠 올리고 오류·비용·문의량을 본 뒤 넓힌다
8. 문제가 나면 앱 판, 서버 기능, AI 기능을 각각 멈추거나 되돌릴 수 있게 한다

Apple은 단순히 웹사이트를 다시 포장한 앱보다 앱다운 지속적 효용을 요구한다.
이 앱은 오프라인 교재와 학습 상태가 있지만, 스토어 시제품에서 그 가치가 앱 안에서
완결되는지 따로 확인한다.

## 6. 실행 단계와 통과 문

### 0단계 · 출시 여부를 결정한다

- 무료/유료 경계, 첫 시장, 플랫폼, 계정 정책을 한 장으로 확정
- AI 글·음성의 비용과 품질 시제품
- 상표·도메인·사업자·세금·지원 책임 확인

**통과 문** — 누가 왜 돈을 내고, 한 사용자가 쓸 때 얼마가 들며, 문제가 생기면
누가 처리하는지 답할 수 있다. 답이 없으면 현재 PWA 개발을 계속하고 구조 전환은 미룬다.

### 1단계 · 기반을 제품 수준으로 옮긴다

- 모듈화·공통 빌드·CI
- 개발/시험/운영 Firebase 분리
- 진도 자료 버전과 이관 시험
- Hosting 시험 주소와 되돌리기

**통과 문** — 운영 사용자에게 손대지 않고 새 판과 자료 이관을 시험할 수 있다.

### 2단계 · 교재와 제품 얼굴을 완성한다

- 3,000문장, 검수, 압축 음성
- 로고·아이콘·첫 화면·디자인 체계
- 접근성·오프라인·저사양 기기 점검

**통과 문** — AI와 결제가 없어도 독립된 완성 교재로 출시할 수 있다.

### 3단계 · AI 회화 비공개 시험

- 학습 프로필, 글 회화, 평가 세트
- 인증·App Check·한도·비용 중지 스위치
- 동의한 시험 사용자에게만 공개
- 통과한 뒤 음성 회화 시제품

**통과 문** — 수준 조절·교정 품질·사용 비용을 실제 기록으로 설명할 수 있다.

### 4단계 · 계정·문의·결제 닫힌 시험

- 탈퇴·내보내기·문의 대기열
- StoreKit·Play Billing·웹 결제 권한 통합
- 갱신·취소·환불·복원 전 과정 시험
- 약관·개인정보·스토어 표기 초안 검토

**통과 문** — 결제가 성공했는데 권한이 없거나, 환불됐는데 권한이 남는 시험 사례가 0건이다.

### 5단계 · 출시 후보

- 스토어 내부/닫힌 시험
- 실제 기기의 설치·갱신·오프라인·마이크·결제 점검
- 고객지원 모의 접수와 장애·되돌리기 연습
- 출시 시점의 Apple·Google·Firebase·Gemini 정책 재확인

**통과 문** — 출시를 막는 오류 0건, 자동 검사 전부 통과, 계정 삭제·구매 복원·
운영판 되돌리기를 실제 환경에서 한 번씩 끝낸다.

### 6단계 · 나눠서 출시한다

- 한 시장·작은 공개 비율부터 시작
- 오류, AI 비용, 결제 실패, 문의량을 매일 같은 지표로 확인
- 기준 안이면 넓히고, 넘으면 해당 기능을 멈추거나 이전 판으로 돌린다
- 첫 안정화 뒤에야 다른 언어·시장·기능을 검토한다

## 7. 서로 기다려야 하는 일

```text
출시·유료 경계 결정
  ├─ 이름 확정 → 상표·도메인 → 로고·스토어 자료
  ├─ 플랫폼 확정 → 앱 껍데기 → 네이티브 결제 → 스토어 심사
  └─ AI 상품 결정 → 비용 측정 → 한도·가격 → 결제 상품

모듈화·환경 분리
  ├─ 계정·자료 이관
  ├─ AI 비공개 시험
  └─ 결제 웹훅·권한

3,000문장 작성은 위와 나란히 계속할 수 있다.
```

결제 화면부터 만드는 순서는 틀렸다. **AI 원가와 권한 구조가 먼저**다.
로고부터 만드는 순서도 위험하다. **이름과 상표 확인이 먼저**다.

- 계정 삭제와 자료 내보내기
- 문의 접수·답변·민감정보 제거

- 앱 아이콘·스크린샷·지원 URL·심사 계정

## 9. 하지 않을 것

- 공개 HTML·JavaScript·앱 꾸러미에 Gemini나 결제 비밀키 넣기
- GitHub Pages만으로 AI·결제 웹훅·관리자 기능까지 떠맡기기

- 회화 원문을 설명과 동의 없이 오래 저장하기
- 실측 전에 「무제한 AI」나 출시일 약속하기
- 결제·AI·네이티브 앱·전체 화면 개편을 한 배포에 함께 넣기
- 현재 작동하는 앱을 한 번에 다른 프레임워크로 다시 쓰기
- Live API Preview 하나만 믿고 글 회화나 기존 학습으로 돌아갈 길 없애기
- 앱스토어 제출 직전에 처음으로 계정 삭제·환불·복원을 시험하기
